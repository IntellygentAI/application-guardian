## 0. Context and ground rules

You are maintaining the open-source skill `IntellygentAI/application-guardian`. It is at version 0.4.0 (commit `4553436`). It already has:

- `SKILL.md` with four modes (Quick Scan, Full Audit, Fix and Verify, Release Gate), read-only rules for audit modes, and a reference map.

- `schemas/`, `templates/`, `evals/` (with `fixtures/` and `expected-results/`), `tests/`, `docs/`, `examples/`, `.github/`.

Do not rebuild the project. Preserve every existing rule, scenario, script behaviour, schema and test. Read every file before changing anything, and write down your planned changes before you make them.

**Goal of v0.5.** The skill covers the right domains, but its references are short checklists. An agent reading "test IDOR" still has to work out what to try, what a vibe-coded app usually gets wrong and what result counts as a pass. v0.5 adds a **scenario playbook**. Every real-world and attacker scenario becomes a concrete, testable item with:

1. The user or attacker action, in plain words.
2. Why AI-generated ("vibe-coded") apps typically fail it.
3. A real-world incident where one exists.
4. The control that must exist, and where it must live (database, server, storage, provider).
5. A safe test using synthetic data, against local or authorised staging only.
6. The pass criteria, with the evidence required.
7. The severity if it fails.
8. An OWASP or CWE reference.

Ground rules that apply to everything below:

- Use only synthetic accounts, fictional data, local environments and authorised staging. Never run these tests against production or anyone else's system.
- Bound every load or concurrency test (for example, 100 parallel requests locally, never unbounded).
- Never print a real secret, token, password hash or personal record in any output. Describe its type and location only.
- Audit modes remain read-only. Only Fix and Verify changes application code, and only after the user asks.
- Do not push, tag, publish a release or change repository settings without my explicit approval.
- Do not invent evaluation results. Anything not executed is `NOT TESTED`.

## 2. Scenario block format

Use exactly this structure for every scenario so that `validate_skill.py` can check it:

```markdown
### AT-02 Change the ID in the URL

- **Action:** A signed-in user changes `/invoices/1042` to `/invoices/1043`.
- **Why vibe-coded apps fail:** Generated CRUD routes fetch by ID without checking that the row belongs to the caller. Sequential integer IDs make this trivial to enumerate.
- **Real-world example:** <only if verified; otherwise omit the line>
- **Required control:** Ownership enforced on the server or by a database policy (`owner_id = auth.uid()` or a tenant check) on every read, update, delete, download and export. Unguessable IDs are extra protection, never the control.
- **Safe test:** Create synthetic users A and B. As A, request B's resource through the UI route, the API route and any server action or RPC. Repeat for update and delete.
- **Pass criteria:** Every attempt returns 403 or 404 with no fields from B's record in the body. B's row is unchanged. Evidence: the executed command, status code and redacted response for each attempt.
- **Severity if it fails:** High (P1). Critical (P0) if the data is health, financial, identity or cross-tenant.
- **References:** OWASP Top 10:2025 A01, OWASP API1:2023 BOLA, CWE-639.
```

Add a check to `scripts/validate_skill.py` so that every scenario block has all of the required fields (Action, Why vibe-coded apps fail, Required control, Safe test, Pass criteria, Severity if it fails, References). It must also check that IDs are unique and that every ID in `scenario-index.md` exists. Add tests for that check in `tests/`.

### 3.1 RW: Real-world user behaviour (video 1)

| ID | Action | What usually breaks | Control and pass criteria |
| --- | --- | --- | --- |
| RW-01 | Paste a 5,000-word bio | No max length anywhere. Unbounded `text` column, layout overflow, and higher AI costs if the bio is summarised. | Server-side schema limit plus database `CHECK` length. The UI wraps or clamps text. Direct API submission returns 400 or 422 with a field message, never 500. |
| RW-02 | Airplane mode in the middle of an upload | Infinite spinner. A half-written row points at a missing file, or a duplicate file appears on retry. | Upload first, then create the record (or use a pending state and clean it up). Show a visible error, a retry button and no orphaned rows. Use resumable or chunked uploads for large files. |
| RW-03 | Rotate the phone during a form, checkout or video | Component remounts and form state is lost. Modals render off-screen. | State survives rotation. No content is clipped in landscape. Test on real devices where possible, and say so when only emulation was used. |
| RW-04 | Make the text size huge | Fixed heights clip text. Buttons overlap or are pushed off-screen. | WCAG 2.2 AA: 200% text and 320 px reflow without loss of function. Use `rem` units and flexible containers. |
| RW-05 | Switch to dark mode, including during use | Hard-coded colours give white text on white. Images and icons become invisible. Contrast fails. | Theme tokens are used everywhere. Contrast is checked in both themes, and a live theme switch causes no flash or state loss. |
| RW-06 | Tap Sign Up twice | Two accounts, two welcome emails or two Stripe customers. A race in the generated "check, then insert" logic. | Unique constraint on the normalised email. The handler is idempotent. Disabling the button helps, but is not the control. 2 parallel requests produce 1 account. |
| RW-07 | Leave the email blank | The client `required` attribute is the only check. A direct API call creates a user with an empty or null email. | Server schema rejects it, and the database column is `NOT NULL` with a format check. The API returns 422. |
| RW-08 | Make the password a single space | A whitespace-only password is accepted, or a trimmed password silently differs from what the user typed. | Reject whitespace-only passwords. Never trim or truncate passwords silently. Enforce length and breached-password rules on the server (NIST SP 800-63B). |
| RW-09 | Open the app on an iPhone 4-sized screen (320 px) | Horizontal scrolling, hidden primary buttons, and modern JavaScript or CSS that an old browser can't run. | Usable at a 320 px width. Unsupported browsers get a graceful message instead of a blank screen. Document the supported browser matrix. |
| RW-10 | Deny every permission | App crashes or loops on the permission prompt. A feature that should still work is blocked entirely. | Ask for each permission in context, explain why, and offer a fallback (for example, upload instead of camera). Revoking a permission mid-session is handled. |
| RW-11 | Sign in with Apple and hide my email | Code assumes a real email, sends to the relay address and breaks, or creates a duplicate account. The name only arrives on the first sign-in and is lost. | Store the Apple `sub` as the identity key. Treat the relay email as valid. Persist the name on the first callback. Link providers only with verification. |
| RW-12 | Quit halfway through onboarding | Half-created profile, so the user is stuck in a redirect loop or crashes on the missing fields. | Onboarding state is stored on the server. The app resumes at the right step, and required-profile guards handle incomplete records. |
| RW-13 | Change my time zone | Bookings shift by hours. "Expires today" is wrong, and the trial ends early or late. | Store UTC. Convert for display only. Server time decides expiry and billing. Test across DST changes and midnight. |
| RW-14 | Switch my phone to Arabic | Layout is not mirrored. Text is hard-coded in English. Numbers and dates are formatted wrongly, and long translations overflow. | Use the `dir="rtl"` and CSS logical properties. Use Intl APIs for numbers, dates and currency. Run a long-string pseudo-locale test. |
| RW-15 | Use the app on slow mobile data | No loading states, timeouts too short, double submits from impatient taps, and huge bundles. | Throttled test (for example, Playwright or DevTools "Slow 3G"): loading states are visible, requests can be cancelled, retries back off and no duplicate writes happen. |
| RW-16 | Delete my account and sign up again | Orphaned rows reattach to the new account by email, old sessions stay valid, or the email is permanently blocked. | Deletion revokes all sessions and removes or anonymises data according to the documented policy. Re-registration gets a clean account with no old private data. |
| RW-17 | Log in on two phones | Last write silently wins. Logging out on one device leaves the other with stale permissions. "Log out everywhere" doesn't exist. | Concurrent edits use versioning or conflict handling. Session revocation is supported, and role changes take effect on the next request. |

### 3.2 AT: Attacker scenarios (video 2)

| ID | Action | What usually breaks | Control and pass criteria |
| --- | --- | --- | --- |
| AT-01 | Put a script in my username | Output rendered with `dangerouslySetInnerHTML`, `v-html`, unsanitised Markdown, or HTML email templates. SVG avatars. | Context-aware output encoding. Sanitise only where HTML is intentional (for example, DOMPurify). Add a CSP. A harmless marker such as `<img src=x onerror=console.log('ag-test')>` is never executed anywhere, including admin views and emails. CWE-79. |
| AT-02 | Change the ID in the URL | Covered in the example in section 2 (IDOR or BOLA). | |
| AT-03 | Just type `/admin` | The admin page is only hidden in the navigation, or only client-side route guards exist. Next.js apps sometimes rely on middleware alone (see VC-08). | Every admin route and API checks the role on the server for each request. An ordinary user gets 403 on the page, the API and server actions. CWE-285. |
| AT-04 | Find your API key in the browser | `NEXT_PUBLIC_`, `VITE_` or `EXPO_PUBLIC_` prefixes on secret keys. AI provider keys called directly from the client. Source maps published. | Secrets stay server-side, and AI calls go through a backend proxy with per-user quotas. Scan built bundles and source maps, not only the source. Publishable keys (Supabase `sb_publishable_`, Stripe `pk_`) are expected in clients and are not findings by themselves. CWE-798, CWE-200. |
| AT-05 | Tell your AI to ignore its instructions | Secrets in the system prompt. Tools run with admin credentials. The model decides authorisation. | Assume injection will sometimes succeed. Tools enforce the caller's permissions independently, there are no secrets in prompts, and output is validated. Sensitive actions need confirmation. OWASP LLM01, ASI01. |
| AT-06 | Make myself admin at signup | The signup handler spreads `req.body` into the insert, so `role: "admin"` is accepted. Supabase `user_metadata` (user-editable) is read for roles. | Allowlist the writable fields. Roles are set only by a server-side process. In Supabase, roles come from `app_metadata` or a protected table, never from `user_metadata`. API3:2023 mass assignment, CWE-915. |
| AT-07 | Edit the price | The price is sent from the cart in the browser to a checkout session or order insert. | The server looks up the price by product or price ID. Stripe Checkout uses `price` IDs, not client amounts. A tampered amount produces a correct charge or a rejection. |
| AT-08 | Fake a payment | Premium is unlocked on the `success_url` redirect or a client "paid" flag. Webhooks are not verified. | Entitlements come only from a signature-verified webhook (or a server-side provider lookup). Check the amount, currency and order owner. Opening `/success` directly grants nothing. |
| AT-09 | Redeem it a hundred times | "Check, then update" coupon logic with no row lock or unique constraint. Classic race condition. | Atomic redemption: a unique `(coupon_id, user_id)` constraint, or a conditional update such as `UPDATE ... WHERE uses < max RETURNING`. A bounded test of 100 parallel local requests produces exactly the allowed count. CWE-362. |
| AT-10 | Order negative one items | Quantity validated only in the UI. Negative totals produce credits or refunds. | Server schema requires a positive integer within a maximum, plus a database `CHECK (quantity > 0)`. Totals are computed on the server in integer minor units. |
| AT-11 | Guess your login code | 6-digit OTP with no attempt limit, no expiry or a long expiry, and reusable codes. | Per-account and per-IP attempt limits with lockout or backoff. Short expiry, single use, constant-time comparison. Test with a bounded fixture (for example, 20 wrong codes), then confirm the limit triggers. CWE-307. |
| AT-12 | Type a query into your database | String-built SQL in raw ORM calls, Supabase `.rpc` functions using dynamic SQL, or NoSQL operator injection (`{"$ne": null}`). | Parameterised queries only. Allowlist identifiers for sort and filter columns. A harmless `'` or `" OR 1=1 --` marker causes a validation error, never a 500 or extra rows. CWE-89, CWE-943. |
| AT-13 | Find your `.env` in Git | `.env` committed before `.gitignore` existed. Secrets remain in history after "deleting" them. | Scan full history (for example, gitleaks). On a hit: report the location and type only, recommend immediate rotation, and remember that removing the file does not revoke the key. CWE-540. |
| AT-14 | Upload something that isn't a photo | Only the extension or browser MIME type is checked. HTML or SVG is served from the app origin, so stored XSS is possible. | Check magic bytes. Re-encode images. Size limits. Random server-generated names. Serve from a separate domain or with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`. CWE-434. |
| AT-15 | Make many accounts or hammer endpoints | No rate limits on signup, OTP, password reset, SMS or AI generation, leading to SMS pumping and AI bill spikes. | Per-user and per-IP limits, CAPTCHA or bot checks on abuse-prone flows, and provider spend caps and alerts. OWASP Top 10:2025 covers this under several categories; also API4:2023. |

### 3.3 DX: Private data exposure (video 3)

| ID | Action | What usually breaks | Control and pass criteria |
| --- | --- | --- | --- |
| DX-01 | Export every user's email | An admin export endpoint missing a role check, or a `select *` on profiles readable by any signed-in user. | Exports need an explicit role, are rate-limited and logged. An ordinary user gets 403. |
| DX-02 | Change the user ID in the URL or body | `/api/users/:id` or `?user_id=` trusted from the client. | The server derives identity from the session, never from a parameter, for "my" resources. |
| DX-03 | Open someone else's invoice | Invoice PDF served by a guessable path or a long-lived public URL. | Authorised download endpoint, or short-lived signed URLs issued only after an ownership check. |
| DX-04 | Read your Supabase tables with the public key | RLS disabled, or a policy of `USING (true)`. The most common vibe-coded critical issue (see VC-01). | RLS is on for every table in exposed schemas, with owner or tenant policies. Test as the `anon` and `authenticated` roles with the publishable key, never the secret key. |
| DX-05 | Read private messages through your API | Message queries filter by conversation ID only, not by participant. Realtime channels are subscribable by anyone. | Participant check on reads and Realtime subscriptions (Supabase Realtime authorisation or Firebase rules). |
| DX-06 | Pull someone's phone number through the profile endpoint | API returns the full row and the UI hides fields. Public profile and private profile share one table. | Explicit response allowlists or DTOs. Separate public and private columns or tables. Inspect raw JSON responses, not the screen. CWE-213. |
| DX-07 | Download everything in a public storage bucket | Bucket marked public for convenience. Listing allowed. Legacy buckets forgotten after a migration. | Private buckets by default, storage policies by owner path, listing denied, and a review of every bucket including old ones. |
| DX-08 | Guess file links because they're numbered | `/uploads/1.pdf`, `/uploads/2.pdf` with no authorisation. | Access control on every file. Random names add defence in depth only. |
| DX-09 | Find password hashes in a response | `select *` from a users table includes `password_hash`, reset tokens or MFA secrets. | Never return credential fields. Keep them in a separate table that clients can't read. A hash is still sensitive (CWE-522). |
| DX-10 | Sweep the user list with an empty search | `ilike '%' \|\| q \|\| '%'` with an empty `q` returns everyone. No page-size cap. | Minimum query length, a capped page size, search limited to deliberately public fields, and rate limits. |
| DX-11 | Grab the database backup in the public folder | `backup.sql`, `dump.json`, `.env.bak` or `.git/` in `public/` or the deploy root. | Build output allowlist. A deploy check for those patterns. Requests to them return 404 on the deployed preview. |

### 3.4 VC: Recurring vibe-coded failure patterns

These are patterns seen repeatedly in AI-generated apps. Confirm each incident against its source before you cite it, and drop any you can't verify.

| ID | Pattern | Notes for the scenario block |
| --- | --- | --- |
| VC-01 | RLS disabled or missing | CVE-2025-48757 (CVSS 9.3): insufficient RLS in Lovable-generated apps let unauthenticated attackers read or write arbitrary tables. A May 2025 scan found 170 of 1,645 sampled apps exposed. Test: list every table in exposed schemas with `rowsecurity = false`. |
| VC-02 | RLS on but `USING (true)` or a missing `WITH CHECK` | Looks secure in the dashboard. Inserts and updates can still change `owner_id` to someone else. Test INSERT and UPDATE as well as SELECT. |
| VC-03 | Inverted access logic | Reported in February 2026: a Lovable-hosted app's generated RPC access check blocked authenticated users and let unauthenticated users in, exposing about 18,000 user records. Always run the negative test (no session) and the positive test. |
| VC-04 | `SECURITY DEFINER` functions and views that bypass RLS | Functions need an internal caller check and `SET search_path = ''`. Views need `security_invoker = true` (Postgres 15 and later). |
| VC-05 | Legacy or forgotten storage | The Tea app breach (July 2025) came from an old Firebase storage bucket left public after a migration. About 72,000 images were exposed, including around 13,000 ID selfies. Audit every bucket and old environment, not only the ones the current code uses. |
| VC-06 | Secret keys in client bundles | AI provider keys, Supabase `service_role` or `sb_secret_` keys, and Stripe `sk_` keys behind public env prefixes. Scan the built output. |
| VC-07 | Firebase rules left in test mode | `allow read, write: if true;` or a time-limited rule that was extended. Use emulator rule tests. |
| VC-08 | Middleware-only authorisation | CVE-2025-29927 allowed Next.js middleware to be bypassed with a crafted header on affected versions. Check the framework version. Authorisation must also happen in the route handler, server action or data layer. |
| VC-09 | Server actions and API routes callable directly | Generated server actions assume they are only called from the form. Test them with direct POSTs as other users. |
| VC-10 | Fail-open error handling | `catch { return true }` or a permission lookup that errors and then allows access. Maps to OWASP Top 10:2025 A10, Mishandling of Exceptional Conditions. Inject a failing permission service in a test and expect denial. |
| VC-11 | Happy-path-only tests | Generated tests cover "user can create an invoice" but never "another user can't read it". The test matrix needs a prohibited case for every permitted case. |
| VC-12 | Mock data left in production paths | Hard-coded demo users, `isAdmin = true` flags, seeded admin passwords, and `if (process.env.NODE_ENV !== 'production')` checks that are inverted. |
| VC-13 | Overprivileged AI agents and MCP tools | An agent with the secret database key or a full filesystem answers for any user. Retrieval does not filter by tenant before data reaches the model. Map to the OWASP Top 10 for Agentic Applications 2026 (ASI01 Agent Goal Hijack and the related tool-misuse and privilege entries). |
| VC-14 | Unbounded AI cost | No output token cap, no per-user quota, agent loops without an iteration limit. Bounded test: confirm the quota triggers. |
| VC-15 | Supply-chain drift | Packages the agent hallucinated or typosquatted, unpinned GitHub Actions, and `postinstall` scripts. Maps to OWASP Top 10:2025 A03, Software Supply Chain Failures. |

Add the matching `references/scenario-index.md` table. It maps changed areas (for example, "signup or auth", "file upload", "checkout", "Supabase migration", "AI tool", "public env var", "storage bucket", "server action", "dependency change") to the scenario IDs that a Quick Scan must run.

## 6. Safe test recipes to include

Put short, copy-ready recipes in the scenario blocks. They must only ever target `localhost` or a staging URL from an environment variable, and only use synthetic users created by the test. For example:

- **RLS check as an anonymous visitor:** request `GET $STAGING_SUPABASE_URL/rest/v1/<table>?select=*&limit=1` with only the publishable key. A private table must return an empty array or an error.
- **IDOR check:** sign in as synthetic user A, call B's resource endpoint, and assert 403 or 404 with no B fields.
- **Race check:** fire N bounded parallel requests (N ≤ 100) with a test token, then assert the database count.
- **Bundle secret scan:** run gitleaks (or an equivalent) over `.next/`, `dist/` or `build/` and any source maps. Report only file paths and secret types.
- **Public artefact check:** request `/.env`, `/.git/HEAD`, `/backup.sql` and `/dump.json` on the preview deployment and expect 404.

Include a header in every recipe: "Run only against environments you own or are authorised to test."
